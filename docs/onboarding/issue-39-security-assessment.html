What the finding means, precisely

RISK 01

Expanded executable supply-chain surface

Development dependencies and package-manager tooling are extra code available inside an Internet-reachable service. Their presence does not prove a vulnerability; it increases the set that must remain trustworthy and patched.

RISK 02

More post-compromise utility

If an attacker obtains application-level code execution, pnpm, Corepack, tsx, source and tests offer more inspectable code and potentially useful command capability than a minimal runtime requires.

BOUNDARY

Source maps and declarations are disclosure/minimization concerns

They reveal implementation detail and make the image larger. They are not, by themselves, evidence of a remote-code-execution defect.

Suggested change: an explicit, inspectable runtime contract

Compile the host deliberately

Emit one stable JavaScript host entry point as a declared build artifact. This removes the runtime need for tsx without rewriting generated JavaScript or relying on hidden compiler paths.

Copy only listed artifacts

Final-stage COPY instructions should mirror the contract exactly. This is safer and more reviewable than copying all packages then trying to delete unwanted output.

Run directly and unprivileged

Use the existing image’s node user with correct ownership, and run node <compiled-host>. This removes the development launcher and reduces root privilege.

Test image contents as a contract

Keep today’s functional route/WebSocket smoke tests and add assertions for non-root UID, absent package manager, and prohibited source/test/map/declaration paths.

Contract conflict

Feature 011 requires no development tooling, but its old command is pnpm host, which depends on the development tool tsx. The desired image cannot exist until the host has a first-class compiled output.

Controls worth keeping

KEEP

Multi-stage build and an official, SHA-pinned Node 24 slim base.

KEEP

Frozen-lockfile installation for reproducible dependency resolution.

KEEP

Single-port `/version`, semantic route, static-asset and WebSocket smoke coverage.

Scope note

Root runtime is a related finding

The current Dockerfile has no USER instruction, so it uses the image-default root user. This is not one of Issue #39’s two named practices, but it is a significant least-privilege improvement to include in the same hardening work. Broad Compose publication is intentional for a self-hosted service; it makes a minimal runtime more important, not inherently wrong.
