## 1. Tokens — single source of truth (FR-003 / FR-004 / FR-005)

Every token below is emitted exactly once into the shared stylesheet's `:root` scope as a CSS custom
property, and exported once from `@europa/design` as a literal-typed `TOKENS` constant. The two
representations carry identical canonical values; the drift check fails on any mismatch or orphan in
either direction (FR-004, G-01). Variable names are generated by the deterministic emitter
(`packages/design/scripts/build-css.ts`) as *prefix + group + kebab-cased key*; every exact spelling
is listed below, so nothing has to be derived by hand.

Each color row states the pairing it participates in, the **measured** contrast ratio, and the WCAG
target, so the accessibility contract is auditable straight from this file (FR-005 / FR-016). Ratios
are computed from the canonical hex values with the WCAG relative-luminance formula and rounded to two
decimals — see § 3 for the full pairing table and the notes that qualify the non-text rows.

Rows in § 1.1–§ 1.8 are the **only** lines in this document that carry a token-variable identifier.
That is deliberate: it lets the coverage guard (G-02) compare this file against the emitted stylesheet
by set *or* by count and get the same answer. Reference tokens from prose by their TS constant
(`TOKENS.color.surface`) or their short token name (`surface`), never by re-spelling the variable.

## 2. Component / class-name catalog — shareable via the single stylesheet (FR-006 / FR-007 / FR-008)

Every class is namespaced `europa-*` and is stable: renaming a catalog class or a token variable is a
breaking change requiring a major bump and a migration note (FR-007, § 6). Additive variants are
non-breaking. The catalog below is exhaustive — the shipped stylesheet defines exactly these selectors
and no undocumented visual class (G-03). Every rule composes tokens only; no rule in the stylesheet
carries a color, spacing, radius, border, shadow, or type literal outside the `:root` block, which is
what makes the same class render identically in React (console) and in plain HTML (Jekyll manual).

Each entry states its accessibility obligations, including the redundant, non-color encoding required

**Measured, not estimated.** These values supersede the planning-time approximations carried in
spec 012 and its contract (`≈ 15:1`, `≈ 13.5:1`, `≈ 6.6:1`, `≈ 16:1`). The deltas are
estimate-versus-computation, not behavior changes: every critical chrome pairing named by FR-016
(page text, HUD text, chip text, muted lines, banner text, focus ring) still clears its AA target.
`DESIGN.md` is authoritative, so the numbers above are the ones G-07 asserts.

**N-1 — focus-ring adjacency.** The ring is painted *outside* the control with a 2px gap, so the color
adjacent to the ring on both sides is the surrounding surface, which is what the table measures. That
gap is part of the contract: without it, the white ring against the amber primary fill would be only
≈ 2.15:1. Never set the offset to zero.

**N-2 — hairline borders are separators, not boundaries.** The canonical border color measures
≈ 1.72:1 against a plate. WCAG 1.4.11 applies to visual information *required* to identify a component
or its state; catalog components are identified by their text label, their fill, and — when focused —
the focus ring, so the hairline is a decorative separator and is deliberately **not** claimed as a 3:1
boundary. Do not build a component whose only cue is this border. Where a real non-text boundary is
needed, use the accent edge (≈ 8.26:1) or the focus ring (≈ 17.74:1).

**N-3 — Canvas terrain fills.** Water against the fog void measures ≈ 2.37:1 and the land band's floor
≈ 1.68:1, both below 3:1. These are Canvas tile fills, not text and not UI-component boundaries, and
terrain identity is redundantly encoded: the elevation band itself spans ≈ 3.78:1 floor-to-ceiling, and
tiles are further identified by troop chips, city markers, and the minimap. This is the inherited
console rendering codified as tokens, not a new decision (spec Assumptions); a future contrast pass on
terrain would change values only, never names (§ 6).

**N-4 — Pipe slope fills on the board.** Pipe indicators render on terrain tiles, so the darkest land
tile (`#3a4a3a`, the land band floor) is the worst-case background: downhill `#059669` measures
≈ 2.51:1 and uphill `#dc2626` ≈ 1.96:1 there, both below the 3:1 non-text target. Against the fog void
(`#1a2233`) all four fills meet ≥ 3:1 (downhill ≈ 4.22:1, flat ≈ 7.40:1, uphill ≈ 3.29:1, stalled
≈ 6.26:1). The fixed three-color slope scheme is spec 005 FR-013's decision (no intensity scaling); the
stalled state is redundantly encoded by a hollow-triangle shape distinct from the filled flowing
triangles. The land band spans ≈ 3.78:1 floor-to-ceiling, so most land tiles are lighter than the floor.
A future contrast pass on terrain would change values only, never names (§ 6).

**Motion (WCAG 2.3.3).** Decorative animation is gated twice: the stylesheet's
`@media (prefers-reduced-motion: reduce)` block collapses animation and transition durations globally,
and `.europa-waiting--reduced` does the same for a host-marked subtree. A focused test asserts the
waiting spinner is inert when the preference is set.

**Focus-visible (WCAG 2.4.7).** One reusable treatment — `.europa-focus-ring` and the shared
`*:focus-visible` rule, built from the § 1.7 tokens — serves every interactive component. Components
use `:focus-visible` rather than bare `:focus` so pointer users are not shown the ring, and no
component may suppress the outline without an equivalent replacement.

**Color-alone prohibition (constitution Principle VI / FR-008).** Every catalog entry in § 2 carries an
explicit "not color alone" sentence naming its redundant encoding — border, text, shape, or position.

## 4. Single-stylesheet, vendoring, and artifact-scope rules

### 4.1 Single stylesheet rule (FR-011)

`@europa/design` ships exactly **one** stylesheet — `packages/design/dist/design.css` — containing the
`:root` token block and every `europa-*` class rule. The console imports it once at its entry and does
not duplicate its rules in a parallel copy; the build output therefore contains a single copy (Vite
dedupes the workspace import). There is no second stylesheet source, no partial re-export, and no
per-surface fork: a new surface gets its look by applying catalog classes, not by adding CSS.

The corresponding console invariant is behavioral, not filename-bound: every `color`, `background`,
`border`, `border-radius`, `gap`, `padding`, `margin`, `box-shadow`, and focus declaration in
`packages/console/src` resolves through a design token variable or a catalog class rather than a
literal, and every color constant in `packages/console/src/render/palette.ts` is derived from `TOKENS`
(FR-009 / FR-010). At most one narrowly-scoped Canvas fallback may be exempt, and it must be marked
with a line-scoped `design-exception: canvas fallback` comment and listed in § 4.4. The no-literals
guard (G-04) fails with `file:line` on anything else.

### 4.2 Vendoring rule — the manual consumes the same file (FR-013 / FR-014)

The shared stylesheet reaches the Pages deployment by being **vendored into the manual tree** as
`docs/manual/assets/design.css`: a byte-identical, checked-in copy produced deterministically by
`pnpm --filter @europa/design build` (sorted keys, LF, UTF-8, no BOM, no timestamp). Because the copy
lives *inside* `docs/manual`, the Pages workflow needs no widening: `actions/jekyll-build-pages` keeps
`source: ./docs/manual` and the uploaded artifact remains exactly the rendered `docs/manual` tree, so
artifact contents stay auditable from that tree alone (FR-013, G-09).
`docs/manual/_layouts/default.html` loads it with
`<link rel="stylesheet" href="{{ '/assets/design.css' | relative_url }}">`.

CI asserts byte identity —
`sha256(packages/design/dist/design.css) === sha256(docs/manual/assets/design.css)` — and fails with
both hashes plus the remediation `run pnpm --filter @europa/design build` when the copy is stale
(G-05). A symlink is not acceptable: Pages builds from a fresh checkout and would not follow a link
out of the scoped source.

### 4.3 No external theme, no CDN (FR-015 / NFR-002)

The manual's Markdown-to-HTML path adds no external dependency. A Jekyll layout or include that pulls
the vendored `assets/design.css` is allowed; a theme gem or a CDN `<link>` is not, and no font is
fetched or bundled — the system's only type stack is the platform stack in § 1.2. If the vendored asset
is ever missing, the manual must still render as readable unstyled HTML and CI must flag the absence.

### 4.4 Documented exceptions

None at this version. The single Canvas-fallback allowance described in § 4.1 is currently unused; if
one is ever introduced, its exact `file:line` and rationale are recorded here in the same commit.

## 5. Sync rule — `DESIGN.md` stays truthful (FR-018 / constitution Principle IV)

**Every change set that alters a token value, adds, renames, or removes a catalog class or a token
variable, or changes an accessibility pairing MUST update `DESIGN.md` in the same commit as the
implementation.** The "specs stay truthful" rule (AGENTS.md workflow rule 4, constitution Principle IV)
extends to this file: a stale `DESIGN.md` is a bug on par with a stale spec. The guards below are part
of the deliverable, not a follow-up, and each fails with an actionable message naming the missing or
extra variable, class, pairing, or file.

Drift guards (see `specs/012-design-system/data-model.md` § Drift Guard):

- **G-01** token-variable ↔ TS leaf identity, both directions (FR-004)
- **G-02** § 1 token-table coverage against the emitted stylesheet (FR-003 / FR-017)
- **G-03** § 2 catalog coverage against the stylesheet's selectors (FR-006)
- **G-04** console no-literals scan (FR-009 / FR-010)
- **G-05** vendored-asset byte identity (FR-014)
- **G-06** version-header lockstep (FR-017 / FR-020 / spec 009 FR-009)
- **G-07** measured contrast for every § 3 pairing (FR-016)
- **G-08** console browser-payload gzip budget &lt; 150 KB (NFR-005)
- **G-09** Pages artifact scope (FR-013)

Every guard runs locally (`pnpm` scripts under `packages/design`) and in CI.

**Editing note for G-02**: keep § 1's tables the only place in this file that spells a token-variable
identifier — one row per token, one row per line. Prose and the § 3 table reference tokens by TS
constant instead. That keeps the coverage guard unambiguous whether it compares sets or counts.

## 6. Extension guidance and light-theme note (FR-019)

This version ships the **dark-slate theme only**. Token *names* and class names are the fixed part of
the contract; token *values* are the variable part. A later light theme is therefore a value
redefinition with no renames:

```css
html[data-theme='light'] {
    /* redefine only the § 1.1 color values — page-bg, surface, text-primary, border, … */
    /* variable names, class names, and DOM structure are unchanged; light values must be */
    /* re-measured against § 3's targets before shipping */
}
```

Light-theme note: the shape admits a light variant, but no light stylesheet, no toggle, and no
dual-theme build ships in this feature (spec Out of Scope). Proposing one is additive and must never
rename an existing variable or class.

Change policy:

- **Adding a variant or an additional token** (for example a danger button modifier, or a new spacing
  step) — **minor** change. Add the catalog or token row in the same commit; no migration note needed.
- **Renaming or removing a token variable or a catalog class, or lowering a documented pairing below
  its target** — **major** (breaking) change. Requires a major-bump discussion and a migration note in
  this file naming the old and new identifiers.

## 7. Build, versioning, and house-keeping (FR-020 / FR-021 / FR-022)

- **Versioning (FR-020)**: this header's `0.1.0` is the current lockstep value and is part of the
  `version:check` surface — it must equal `packages/design/package.json#version`, `APP_VERSION`, and
  every other `package.json#version`, with no special case. Bumps follow spec 009's
  `chore(release): vX.Y.Z` convention (see the header's "How to bump").
- **Build order (FR-021)**: `pnpm build` builds `@europa/design` before `@europa/console`, and the
  design build vendors the stylesheet into `docs/manual/assets/` as a post-build step, so a clean
  checkout reaches a built console and a styled manual in one command. Running the design build twice
  is idempotent.
- **Biome and CI coverage (FR-022)**: `biome.jsonc` covers `packages/design/**` under the repo's
  standard formatting rules with no formatter suppression. Workflow path filters (`client-ci.yml`,
  `pages-deploy.yml`, `version-drift.yml`) include `packages/design/**`, `DESIGN.md`, and the vendored
  asset path so a change to any design surface triggers the right checks — without widening the Pages
  artifact scope (§ 4.2).
