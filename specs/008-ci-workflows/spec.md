## Problem Statement

Downstream CI workflows don't accurately reflect upstream package dependencies in their `paths` triggers. Additionally, the workflows lack operational hardening features (concurrency groups, manual triggers, automated dependency updates) that are standard for production CI pipelines.

Beyond trigger correctness, the coverage-gate infrastructure has systemic integrity gaps: the console coverage config's a11y include glob is `tests/a11y/**/*.test.ts` while five `.tsx` a11y suites exist (~1,355 LOC never measured by `pnpm coverage`/the `console-coverage` CI job), `src/internal/**` (~3,022 LOC / 12 files) is excluded from all three console vitest configs, `@europa/design` and `@europa/version` suites run in no CI workflow (design's browser config is orphaned — `vitest.config.browser.ts` exists but no CI job references it), and design's coverage config excludes its own guard scripts. A coverage gate that doesn't execute what it claims is worse than no gate — it provides false confidence.

As of the v1.4 amendment (2026-10-13, verified against the tree), two further systemic gaps exist. First, `scripts/verify.sh` is not CI-equivalent: CI runs gates that no local gate runs (the `host-smoke-n-players`, `semantic-route-security`, and `semantic-url-privacy` console integration suites — which CI executes only via the console coverage config's node project — the runtime `contract-conformance` suite, the `@europa/core` coverage gate, and the `@europa/logging` test suite), so a red one of these passes `pnpm verify` and fails only at CI. Second, the contract "type witnesses" that specs 002/004/010 rely on never compile: every package tsconfig excludes `tests/` by design and vitest does not type-check, so the witnesses degenerate to runtime `expect(true).toBe(true)` keep-alives — only console and matchmaking even ship a `tsconfig.conformance.json`, matchmaking's program is invoked by no workflow, and networking and fog have none. Additionally, 13 workflows hand-rolled the prologue's `pnpm-setup` step at v1.4 (9 of them including workspace build chains; the nine package workflows were consolidated by that amendment, while five non-package workflows still hand-roll `pnpm/setup` under FR-026's exemption), package path filters watch direct dependencies only and miss transitive ones (verified: `matchmaking-ci.yml` omits `packages/fog/**` via matchmaking→networking→fog; `engine-ci.yml` omits `packages/terrain/**` despite engine's `@europa/terrain` devDependency), and this spec's own v1.0 acceptance criteria still say "6 CI workflows" while `.github/workflows/` shipped 15 at the v1.4 amendment (2026-10-13).

As of the v1.8 amendment (2026-10-27, issue #223, verified against the tree and the Actions run API), CI is flaky on a class of failure the gates do not own, and it pays the same setup 29 times per full run. Playwright is installed at four sites — `client-ci.yml` `design-browser-test`, `console-e2e`, `console-coverage`, and `manual-ci.yml` — of which two pass `--with-deps` (apt system libraries on every run) and two do not (`design-browser-test`, `manual-ci.yml`), so the two that skip apt are the ones whose browser launch depends on whatever libraries the runner image happens to carry. Three `~/.cache/ms-playwright` caches (`client-ci.yml` twice, `manual-ci.yml` once) key on `hashFiles(...lockfile)` with no Playwright version and no `restore-keys`, so a partially restored store can mix browser builds. All 50 job definitions across the 15 workflows pick a runner explicitly — 48 on `ubuntu-latest` and 2 on `ubuntu-24.04` (`docker.yml`) — so an OS or library change arrives without review: run 34645970848 and run 34645294378 (2026-09-11) both died at `sh: 1: playwright: not found`. Separately, 38 jobs exist across the nine package workflows and 29 of them invoke `.github/actions/build-workspace` — install plus ordered dependency builds, 29 times per full run; those 29 jobs are direct children of `changes` and run in parallel, so the repetition costs runner time and multiplies the setup-flake surface rather than lengthening the critical path by itself. The gating cost is elsewhere: in that run `Test suites (console — browser)` is 302 s against the next-largest job's 118 s, and deduplicating the prologue was evaluated and rejected — a single serial prepare stage plus its hand-off adds 20–50 s to every workflow's critical path, past NFR-012's allowance on most of them (FR-039's tombstone) — so this amendment attacks the longest job instead (FR-045/FR-046). Per-job durations from the last green `main` `Client CI` run (40399256099) are context, not a like-for-like baseline: 302 s for `Test suites (console — browser)`, 118 s for `Coverage gate (console ≥ 80%)`, 98 s for `Test suites (console — node)` — each is that job's figure in that run, and they do not come from a single attempt of it (the like-for-like comparison is per workflow, NFR-012). And one browser-suite flake is not an install problem at all: run 40035460998 (2026-10-23) lost `tests/component/render/pipe-slope.test.tsx` to `Failed to fetch dynamically imported module` after Vite logged `dependency optimized: react-dom/client` and `optimized dependencies changed. reloading` — even though `packages/console/vitest.config.browser.ts` already lists that entry in `optimizeDeps.include`, and the coverage config's browser project has no `optimizeDeps` block at all.

## User Stories

- **US1**: As a contributor, I want CI to trigger only when relevant code changes so that I don't wait for unrelated pipelines.
- **US2**: As a maintainer, I want automated tool for keeping pinned action SHAs current so that security patches arrive without manual effort.
- **US3**: As a contributor, I want to manually re-trigger CI after transient failures so that I don't need empty commits.
- **US4**: As a maintainer, I want concurrent pushes to not waste runner resources so that CI costs stay reasonable.
- **US5**: As a maintainer, I want every coverage gate to execute exactly the tests it claims so that I can trust the ≥80% threshold (Constitution III).
- **US6**: As a contributor, I want a CI job that fails if a vitest config file exists but no script or workflow references it, so that orphaned configs are caught before they drift.
- **US7**: As a contributor, I want `pnpm verify` to run exactly the gates CI runs — including the integration, security, privacy, and conformance suites — so that a green local run means a green PR (issue #133).
- **US8**: As a maintainer, I want every package's contract type witnesses compiled by a dedicated strict program wired into CI and `pnpm verify`, so that mirror drift fails the gate instead of silently degenerating to `expect(true).toBe(true)` (issue #144).
- **US9**: As a maintainer, I want the browser and its system libraries to come from an image Playwright publishes at the exact version we run, so that nothing installs at run time and a runner-image change cannot turn a required check red for reasons a contributor cannot reproduce locally (issue #223).
- **US10**: As a contributor, I want the longest job in the critical path split and sharded rather than the parallel prologues deduplicated, so my PR finishes sooner instead of merely doing less repeated work (issue #223).

### Commit-Message Hygiene (v1.3 — bot co-author trailers)

- **FR-018**: A commitlint configuration MUST exist at the repo root that extends `@commitlint/config-conventional` (enforcing the Constitution's Conventional Commits rule) AND adds a custom rule forbidding bot co-author trailers. The custom rule MUST reject any commit message containing a `Co-authored-by:` trailer whose name matches Copilot or Claude (case-insensitive, any casing/version suffix, e.g. `Claude Opus 4.5`). Rationale: GitHub's squash-merge preserves co-author trailers from branch commits, which put bot accounts on the repository's Contributors list.
- **FR-019**: A husky `commit-msg` hook MUST run commitlint on every local commit (via `pnpm exec commitlint --edit "$1"`), so a commit with a non-conventional message or a bot co-author trailer is rejected at commit time.
- **FR-020**: A CI workflow MUST lint the PR title with commitlint on every pull request to `main`. The PR title becomes the squash-merge commit subject, so it must satisfy the same rules as a local commit header.
- **FR-021**: The same CI workflow MUST lint every non-merge commit in the PR range (`base.sha..head.sha`) with commitlint, catching bot co-author trailers in branch commits before GitHub's squash-merge can preserve them into `main`. Merge commits MUST be excluded from the lint (their messages are not conventional).
- **FR-022**: The commitlint configuration MUST be a TypeScript file (`commitlint.config.ts`) consistent with the repo's TS-first tooling, and the dependencies (`@commitlint/cli`, `@commitlint/config-conventional`) MUST be pinned in the pnpm catalog and root `devDependencies`.
- **FR-023**: The commitlint CI workflow MUST follow the existing hardening patterns: SHA-pinned actions with version comments, `concurrency` group, `workflow_dispatch`, and `contents: read` permissions. It MUST NOT be path-gated — commit hygiene applies to every PR regardless of which files changed.

### Conformance-Program Wiring (v1.4 — Issue #144, review ref I-13)

- **FR-029**: Each contract-bearing package MUST ship a dedicated strict typecheck program `tsconfig.conformance.json` plus a `typecheck:conformance` script whose include set compiles the package's contract-conformance witness test file(s) alongside `src/` — closing the documented tradeoff that every package tsconfig excludes `tests/` and vitest does not type-check. Required set at amendment time: `packages/console` (exists — must stay green), `packages/matchmaking` (exists), `packages/networking` (missing — must be created, compiling `packages/networking/tests/contracts-conformance.test.ts`), `packages/fog` (missing — must be created, compiling `packages/fog/tests/conformance.test.ts`). A program MUST NOT exist without being invoked (no middle state).
- **FR-030**: Every `typecheck:conformance` program MUST be invoked in its package's CI workflow (`client-ci.yml` — already wired, `matchmaking-ci.yml` — exists but invoked by no workflow, `network-ci.yml`, `fog-ci.yml`) AND in `scripts/verify.sh`. At amendment time only console's program is wired in both places; matchmaking's `tsconfig.conformance.json` + script exist but run nowhere.

## Edge Cases

- Dependabot grouping: all action updates should be grouped into a single PR to avoid PR noise.
- Concurrency group key: uses `github.head_ref` for PRs (cancels outdated PR runs) and `github.run_id` for push runs (never cancels push runs).
- `src/internal/` files that are genuinely untestable (e.g., DOM-bound entry points only exercised by real-socket integration): exclude them individually with a `// Untestable: <reason>` comment. Blanket directory exclusion is forbidden after this change.
- Design browser config orphan: if `vitest.config.browser.ts` exists but no npm script points to it, the orphaned-config guard catches it. The fix is to wire the script, not delete the config.
- New packages added in the future: the orphaned-config guard automatically covers them — any new `vitest.config*.ts` must be referenced or CI fails.
- Adding a workspace dependency to a package changes its workspace-dependency-closure path filters (FR-027); the workflow filters MUST be extended in the same change set.
- A change to `.github/actions/build-workspace` affects all nine package workflows at once: the action stays minimal (setup + install + dependency builds only); `concurrency` groups, `permissions`, and change-detection jobs remain per-workflow.
- Upstream image pull (v1.8): `mcr.microsoft.com/playwright:v<version>-noble` is public, so a fork PR pulls it anonymously with `contents: read`; there is no package of ours to make public and no credential to add.
- `changes` jobs (v1.8): stay on the host by FR-038 — they run on every PR and gate every other job in their workflow, so an image pull before their first step would tax all nine workflows, docs-only PRs included, for a job that runs no browser.
- A new contract-witness test file MUST be added to its package's `tsconfig.conformance.json` include set in the same change set; a witness outside the program degrades to a vitest-only run (the exact failure mode FR-029 eliminates).
- Tag bump / Playwright bump (v1.8): the catalog entry, the workflow tag and the resolved `playwright-core` move together in one PR, with no publish window in between because nothing is published here; NFR-014's equality check fails loudly when one is missed, and rollback is the same one-line revert.
- Fork PR (v1.8): nothing is published, so a fork takes the same anonymous pull as `main`; a fork that cannot pull is a registry problem to report, not a permissions problem to work around.
- In-image toolchain (v1.8): several jobs run `pnpm` inside the image and none may download Node (FR-047); if a setup step cannot be told to skip the runtime, activate pnpm via corepack instead — an in-job Node install is not acceptable.
- Shard imbalance (v1.8): three legs need not take equal time; the measured two-leg split was 170 s / 192 s because `selfhost.spec.ts` and the `full-stack*` specs landed together, and the leg that matters is the slowest — which is why FR-046 records the measured basis for three and leaves any further change to measurement.
- Matrix check names (v1.8): GitHub suffixes each matrix leg, so the e2e job appears as three required checks; FR-040's before/after table and the maintainer action must name all three.
- A job that genuinely needs a tool the image lacks (v1.8): the image is upstream's and cannot be extended here, so such a job stays on the host with `pnpm/setup` and installs what it needs; a job that starts launching a browser joins the browser-launching set in FR-038 (seven jobs at amendment time — see FR-038's amended note).
- Unrelated PR (v1.8): `changes` reports false and its gates report as skipped — the required-check semantics documented at the top of `client-ci.yml` are preserved, not replaced by a silent success.
