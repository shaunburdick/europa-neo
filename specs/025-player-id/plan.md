# Plan: Replace Numeric PlayerId with Stable Server-Generated String Identifier

**Feature**: 025-player-id  
**Spec References**: Spec 001 FR-020/FR-021, Spec 004 v1.5, Spec 005 v1.18, Spec 006 v1.3  
**Branch**: `issue-74-player-id`  
**Constitution Alignment**: Principles II (determinism), III (simplicity), IV (specs-as-documentation)

---

## 1. Problem Statement

The current `PlayerId` type (`1 | 2 | 3 | 4`) is a numeric union that:
- Couples seat index to identity (seat 0 always = player 1)
- Cannot support reconnect-by-id (seat reassignment after disconnect loses identity)
- Prevents future multi-session or spectator-to-player promotions
- Makes the wire protocol fragile (numeric PlayerId in JSON is indistinguishable from a bare integer)

**Goal**: Replace with a branded string type (`string & { __brand: 'PlayerId' }`) generated by NanoID, enabling stable server-assigned identity independent of seat order.

## 2. Architecture Overview

### 2.1 The Internal-Index / External-ID Pattern

The engine's `WorldState` uses `Uint8Array` for `troopOwners` and `cityOwners` (1 byte per cell — critical for tick performance on 32×32+ boards). String PlayerIds cannot fit in a single byte. The solution is an **internal-index / external-ID dual representation**:

```
External world (public API):     string PlayerId ("AbC123xYz90Q")
         ↕  PlayerRegistry
Internal world (WorldState):     numeric index  (0, 1, 2, 3)
```

- `WorldState.troopOwners` / `cityOwners` stay `Uint8Array` using **0-based player indices** (unchanged performance characteristics).
- `PlayerRegistry` (held by `World`) maps between string IDs and numeric indices.
- `CityPlacement.owner` stays numeric (board contract unchanged — terrain generates with numeric owners).
- `Order.player` carries the **string PlayerId** (the public type).
- `tick()` sorts orders by `player.localeCompare(other)` (FR-017 clarified).

### 2.2 Why Not Refactor WorldState to Maps?

- `Uint8Array` access is O(1) with no heap allocation — critical for the inner tick loop.
- Maps/objects would add pointer chasing and GC pressure on every cell access.
- The numeric-index layer is a well-understood pattern (similar to entity-component systems).
- Determinism: typed arrays produce identical binary output across JS engines; object property order is implementation-defined.

## 3. Package-by-Package Changes

### 3.1 `@europa/core` (types.ts)

| What | Change |
|------|--------|
| `PlayerId` type | `string & { readonly __brand: 'PlayerId' }` |
| `ENGINE_API_VERSION` | Bump `0.1.0` → `0.2.0` |
| New export | `generatePlayerId(): PlayerId` — NanoID 12-char (FR-021) |

**NanoID rationale**: 12-char alphanumeric = 62^12 ≈ 3.2 × 10^21 possibilities. Compact, URL-safe, collision-resistant for match-scale use. No external dependency — inline implementation using `crypto.getRandomValues`.

**`CityPlacement.owner`**: Stays numeric (matching `WorldState` owner bytes). The board contract is a terrain→engine boundary; terrain does not know about string PlayerIds. `createWorld` maps numeric owners to string IDs via position.

### 3.2 `@europa/engine` (core logic)

#### 3.2.1 New: `PlayerRegistry`

A small, pure mapping object held by `World`:

```typescript
export interface PlayerRegistry {
    /** String PlayerId at internal index `i`. */
    idAtIndex(i: number): PlayerId;
    /** Internal index for a given string PlayerId. */
    indexOfId(id: PlayerId): number;
    /** All IDs in deterministic order (sorted by localeCompare). */
    readonly sortedIds: readonly PlayerId[];
    /** Player count. */
    readonly size: number;
}
```

Factory: `createPlayerRegistry(ids: readonly PlayerId[]): PlayerRegistry`

- Validates: all non-empty strings, all unique, length ∈ [2, 4].
- `sortedIds` is pre-computed at construction (stable across all calls).
- `indexOfId` uses a `Map<string, number>` for O(1) lookup.

#### 3.2.2 `MatchConfig` Changes

```typescript
export interface MatchConfig {
    readonly boardSize: number;
    readonly playerIds: readonly PlayerId[]; // replaces playerCount
    readonly tickIntervalMs: number;
    readonly seed: number;
    readonly visibilityRadius: number;
}
```

`playerCount` is DERIVED: `config.playerIds.length`. No separate field.

#### 3.2.3 `World` Changes

```typescript
export interface World {

    readonly tick: number;
    readonly board: Board;
    readonly players: ReadonlyArray<Player>;
    readonly state: WorldState;
    readonly rngSeed: number;
    readonly rngState: Readonly<Uint32Array>;
    readonly playerRegistry: PlayerRegistry; // NEW

```

#### 3.2.4 `Player` Changes

```typescript
export interface Player {
    readonly id: PlayerId;  // was numeric, now string
    readonly displayName: string;
    readonly status: PlayerStatus;
    readonly citiesOwned: number;
    readonly troopsHeld: number;

```

The `id` field type changes from `1|2|3|4` to `string & __brand`.

#### 3.2.5 `createWorld` Changes

```typescript
export function createWorld(config: MatchConfig, board: Board): World
```

New validation:
- `config.playerIds` must be a non-empty array of unique non-empty strings, length ∈ [2, 4].
- Build `PlayerRegistry` from `config.playerIds`.
- City `owner` (numeric) maps to internal index directly (0-based = `owner - 1` for 1-based terrain owners).
- Players created with string IDs from the registry.

#### 3.2.6 `read.ts` Changes

- `getPlayer(world, id)`: `id` is now `PlayerId` (string). Look up via `world.playerRegistry.indexOfId(id)`.
- `alivePlayers(world)`: Returns `PlayerId[]` (strings) in registry order.
- `CellView.troopOwner` / `cityOwner`: Now `PlayerId | null` (string), resolved from internal byte via `world.playerRegistry.idAtIndex()`.

#### 3.2.7 `tick.ts` — Order Sorting

```typescript
// Before (numeric):
if (a.player !== b.player) {
    return a.player - b.player;
}

// After (string, FR-017 clarified):
if (a.player !== b.player) {
    return a.player.localeCompare(b.player);
}
```

This is the **determinism-critical** change. `localeCompare` with default locale produces a stable total order across JS engines for ASCII alphanumeric strings (which NanoID guarantees).

#### 3.2.8 `serialize.ts` Changes

Binary format changes (VERSION BUMP — existing serialized data is incompatible):

**Player record** (currently: 1-byte id):
```
Before: [1 byte: id as uint8]
After:  [1 byte: id string length] [N bytes: ASCII id string]
```

**City record** (currently: `owner` as 1-byte uint8):
Stays 1 byte (numeric owner index). No change.

**Cell records**: Unchanged (troopOwners/cityOwners stay uint8 — numeric indices).

**New player ID table** (prepended to player block):
```
[1 byte: player count]
Per player: [1 byte: id string length] [N bytes: ASCII id string]
```

The per-player record below the table uses the table index (0-based) for the serialized `id` field (backward-compatible index). On deserialize, the ID table is read first, then player records reference it.

`ENGINE_API_VERSION` bumped → `deserializeWorld` rejects old buffers.

#### 3.2.9 Resolution Modules

Internal engine modules (`combat.ts`, `capture.ts`, `flow.ts`, `decay.ts`, `production.ts`, `paratroop.ts`, `gun.ts`) operate on `WorldState` typed arrays using **numeric indices**. These modules are **unaffected** by the PlayerId type change — they never see string IDs. The index-to-ID conversion happens only at the `World`/`Player` boundary.

Exception: `terminal.ts` builds `Player` objects — these now get string IDs from the registry.

## 4. Determinism Analysis (SC-001)

### 4.1 What Changes

| Operation | Before | After | Deterministic? |
|-----------|--------|-------|---------------|
| Order sort | `a.player - b.player` (numeric) | `a.player.localeCompare(b.player)` (string) | ✅ Yes — NanoID is ASCII alphanumeric; `localeCompare` is stable for same-locale, same-string comparisons |
| `createWorld` | `(i + 1) as PlayerId` | `config.playerIds[i]` | ✅ Yes — IDs are inputs, not random |
| Serialization | `out[p++] = player.id & 0xff` | Length-prefixed ASCII | ✅ Yes — fixed encoding |
| `WorldState` arrays | Numeric indices | Same numeric indices | ✅ Yes — unchanged |

### 4.2 What Does NOT Change

- `WorldState` typed arrays (still `Uint8Array`/`Uint32Array`).
- Resolution modules (`combat.ts`, `capture.ts`, etc.) — operate on numeric indices.
- PRNG stream consumption — PlayerId never enters PRNG.
- Board/cell structure — unchanged.

### 4.3 Regression Strategy

1. Run existing `hashWorld` determinism test after migration — byte-identical output for same inputs (same seed, same player count → same sorted IDs → same world state).
2. New test: 10k-tick determinism with string PlayerIds.
3. Golden fixture regeneration for `golden-1000-tick.json`.

## 6. Risk Assessment

| Risk | Likelihood | Impact | Mitigation |
|------|-----------|--------|------------|
| `localeCompare` non-determinism across engines | Low | Critical | NanoID is ASCII-only; test on V8 + SpiderMonkey; add byte-identical determinism test |
| Serialization format change breaks golden fixtures | Certain | Medium | Regenerate all golden fixtures in same change set |
| `Uint8Array` owner byte reinterpreted as string | High | High | Strict type boundary: `WorldState` stays numeric internally; conversion at `getCell`/`getPlayer` only |
| Performance regression from string comparisons in sort | Low | Low | String `localeCompare` is O(k) where k = string length (12 chars constant); negligible vs hash map lookups |
| Test suite breakage from type change | Certain | Low | Mechanical fix: every `as PlayerId` cast on numbers must become a string brand assertion |

## 7. Key Decisions

1. **NanoID 12-char over UUID v4**: Shorter, more compact on the wire, sufficient entropy for match-scale IDs. UUID v4 is 36 chars — wasteful for something that appears on every order and tick.

2. **Internal index stays numeric**: `WorldState` typed arrays use 0-based indices. This is a well-understood entity-component pattern and preserves the performance-critical inner loop.

3. **`CityPlacement.owner` stays numeric**: The board is a terrain→engine boundary. Terrain has no concept of string PlayerIds. `createWorld` maps numeric owners to internal indices.

4. **`requestedSeat` stays numeric on the wire**: Clients request a seat number (0-based); the server maps it to a string PlayerId. This keeps the join protocol simple — clients don't need to know PlayerIds before joining.

5. **No backward compatibility**: Pre-1.0 software. Clean break. Old serialized data is rejected by version check.

6. **PlayerIds generated at match start (filling→running)**, not at seat fill: This ensures the server assigns all IDs atomically, and seat assignments during filling use provisional numeric indices that are replaced at start.
