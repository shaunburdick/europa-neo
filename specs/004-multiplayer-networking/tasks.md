## Phase 3: User Story 1 - Authoritative Real-Time Match Channel (Priority: P1) 🎯 MVP

**Goal**: Deliver the server-authoritative WebSocket channel that accepts orders from clients, runs the deterministic tick loop, and broadcasts fog-filtered `PlayerView` per recipient. After this phase, a 2-player scripted match can be driven end-to-end via `MockWebSocket` clients: orders in, per-tick deltas out, zero fog violations, zero rate-limit leaks, zero schema rejections on valid input. The MVP is the `createMatchServer` factory + the per-match `MatchChannel` orchestrator.

**Independent Test**: Per `quickstart.md` Q-N01: boot an in-memory `createMatchServer` with the real `@europa/engine` and `@europa/fog` deps; `server.registerMatch(...)` + `server.attachPlayer(...)` for two players; two `ScriptedClient` instances connect, send `hello` + `joinMatch`; one client sends 5 valid `Order` messages (e.g., pipe-build) at the spec rate; assert (a) each order gets a `orderAck` within 100 ms (SC-002), (b) both clients receive exactly one `tick` envelope per scheduler fire (250 ms by default, accelerated to 50 ms in the quickstart), (c) each client's `tick.view.visibleCells` is exactly the fog horizon of that player's stacks, and (d) one client sending an invalid order (pipe into water) gets a `orderAck.ok: false` and the world's `pendingOrders` queue is unaffected on the next tick.

**⚠️ MVP scope clarification**: The MVP in this phase handles the **non-reconnect, non-spectator** path of `createMatchServer` only. The reconnect lifecycle (`src/reconnect.ts`, `src/resync.ts`) is added in US2 (Phase 4). The spectator path (`src/spectator.ts`) is added in US3 (Phase 5). The `Server` interface declared in `contracts/network-api.ts` already exposes the full surface (`registerMatch`, `attachPlayer`, `detachPlayer`, `enableSpectators`, etc.); US1 ships a working subset, US2/US3 add the remaining methods without changing the public types.

## Implementation Strategy

### MVP First (Phase 1 + 2 + 3)

The MVP for feature 004 is **Phase 1 + Phase 2 + Phase 3 (US1)**. It delivers a `createMatchServer` factory that boots an in-memory match server, accepts orders, runs the deterministic tick loop, and broadcasts fog-filtered `PlayerView` per recipient. The MVP proves:

1. The `packages/networking` package scaffolding is sound.
2. The wire transport (WebSocket + JSON + envelope + version check) is round-trip-clean.
3. The per-tick pipeline (drain orders → advance engine → broadcast) is end-to-end functional.
4. The package's public surface (`createMatchServer`, `Connection`, `MatchChannel`, all types and constants) is importable from `@europa/networking`.
5. SC-001 protocol-level determinism is proven at the byte-identical-frame level.
6. Spec FR-001, FR-002, FR-003, FR-004, FR-005, FR-006, FR-008, FR-010, FR-011 are all green.

**MVP delivery sequence:**

1. Complete Phase 1: Setup.
2. Complete Phase 2: Foundational (CRITICAL — blocks all stories).
3. Complete Phase 3: User Story 1.
4. **STOP and VALIDATE**: `pnpm --filter @europa/networking test` runs T021–T024, T030, T032, T033 green; coverage ≥80% on `src/`; the SC-002 100 ms order-to-ack is met on localhost; the SC-004 byte-identical frames assertion is green.
5. Do NOT proceed to US2/US3 until US1 is merged. The MVP is sufficient to unblock feature 005 (console can import the contracts) and feature 006 (matchmaking can call `createMatchServer` for the binary shell); reconnect and spectator are follow-ups.

### Incremental Delivery

1. **Setup + Foundational** → `pnpm install` clean, `pnpm build` produces `dist/`, types and wire utilities importable, fixtures usable from tests.
2. **+ User Story 1** → MVP! `createMatchServer` works end-to-end with real engine + fog; deterministic; rate-limited; fog-filtered.
3. **+ User Story 2** → Reconnect with state resync + bounded event replay. US2 ships two new modules and a `server.ts` extension.
4. **+ User Story 3** → Spectator attach + full-board routing. US3 ships one new module and a `server.ts` extension.
5. **+ Polish** → Conformance test enforces the engine ↔ networking boundary, SC-005 perf budget proven, README published, CI gating merges, spec status flipped to `Implemented`.

Each story adds value without breaking the previous story's acceptance tests.

### Parallel Team Strategy

With multiple dispatchers (the recommended approach for a feature this size per the `orchestration` skill):

1. **Phase 1 + 2** together (foundational setup is sequential by nature).
2. **Phase 3** by a single dispatcher (the algorithm chain `Connection` → `MatchChannel` → `orders` → `broadcast` → `stats` → `server` has tight within-phase ordering; the integration tests at the tail can fan out).
