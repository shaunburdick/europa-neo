# Research: Design Polish

**Feature**: 062-design-polish | **Date**: 2026-09-03 | **Spec**: [`spec.md`](./spec.md)

This document captures the technical research and decisions that inform the implementation plan. It focuses on the areas where the spec leaves room for interpretation or where prior art / best practices inform the approach.

---

## R1: CSS-only tooltip patterns

The spec (FR-019) requires a CSS-only tooltip using the `data-tooltip` attribute with `::after`/`::before` pseudo-elements. This is a well-established pattern:

```css
.europa-tooltip {
    position: relative;
}
.europa-tooltip::after {
    content: attr(data-tooltip);
    position: absolute;
    bottom: 100%;
    left: 50%;
    transform: translateX(-50%);
    opacity: 0;
    pointer-events: none;
    transition: opacity var(--europa-motion-transition-fast) var(--europa-motion-easing);
}
.europa-tooltip:hover::after {
    opacity: 1;
}
```

**Considerations**:
- **Viewport clipping**: The tooltip may clip at viewport edges. The spec explicitly accepts this (Edge Cases section) — no JS repositioning.
- **A11y**: The tooltip is supplementary (redundant with visible text). It is not announced by screen readers (purely visual). This is acceptable per the spec.
- **Focus**: Keyboard focus does not trigger the tooltip (hover-only). Acceptable because the content is redundant.
- **Arrow**: A `::before` pseudo-element creates a CSS triangle. The triangle must match the tooltip plate background color (`--europa-color-surface`).

**Decision**: Use the standard `data-tooltip` + `::after`/`::before` pattern. No JS, no `aria-describedby` (content is redundant).

## R2: Responsive breakpoint strategy

The spec (FR-022..025) defines breakpoints at 480px, 768px, and 1200px. These are mobile-first with explicit desktop behavior.

**Considerations**:
- The existing `.europa-lobby__grid` uses `grid-template-columns: repeat(auto-fit, minmax(17rem, 1fr))` — this already stacks to single column below ~17rem per card. The explicit breakpoints make this behavior deterministic and testable.
- The HUD horizontal layout at ≥1200px is a significant layout change — the HUD currently is a vertical column. The flex-wrap + `align-items: baseline` approach keeps sections aligned while wrapping.
- The modal responsive width at ≤480px (`max-width: calc(100vw - 2rem)`) ensures the modal fills most of the viewport on phones.

**Decision**: Use the spec's breakpoints verbatim. No new breakpoint variables — inline media queries in the CSS.

## R3: `backdrop-filter` graceful degradation

The spec (FR-014, FR-036) uses `backdrop-filter: blur()` for the modal backdrop and waiting overlay.

**Considerations**:
- `backdrop-filter` is supported in Chrome 76+, Safari 9+, Firefox 103+. Older Firefox (< 103) ignores it.
- The modal/waiting overlay already has a solid `overlay-strong`/`overlay-soft` background — the blur is additive, not essential.
- No `@supports` guard is needed — the property degrades gracefully (browser ignores unknown property).

**Decision**: Use `backdrop-filter` directly. No `@supports` wrapper. The overlay background provides the fallback.

## R4: `cubic-bezier(0.16, 1, 0.3, 1)` easing curve

The PO ruled (D3) that `easingOut` uses `cubic-bezier(0.16, 1, 0.3, 1)` — the "ease-out-expo" curve.

**Characteristics**:
- Starts fast, decelerates smoothly to rest.
- Feels more organic/polished than the default `ease-out`.
- Commonly used in modern design systems (e.g., Material Design's "standard" curve is similar).

**Decision**: Use the PO-ruled value. This is a single token value — no structural impact.

## R5: `tokens.json` generation

The spec (FR-006) requires a `--emit-json` mode in `build-css.ts` that writes `dist/tokens.json`.

**Design**:
- One entry per CSS variable with `name`, `value`, and `group` fields.
- Sorted lexicographically by CSS variable name (matching the CSS emitter's determinism).
- Gitignored (build output).

**Consumers**:
- The preview page (FR-042) reads `tokens.json` to build token tables.
- Documentation generators can consume it for DESIGN.md drift checks.
- Tooling can consume it for design-token linting.

**Decision**: Extend `build-css.ts` with a `--emit-json` flag. The JSON emitter reuses the existing `collectEntries()` function — no duplication.

## R6: Contrast-notes machine-readable file

The PO ruled (G9) that contrast pairings are emitted as a machine-readable JSON/YAML file for drift tests.

**Design**:
- `dist/contrast-notes.json` — one entry per pairing with `foreground`, `background`, `ratio`, and `target` fields.
- Generated by a new `generate-contrast-notes.ts` script that computes WCAG relative-luminance ratios from the token table.
- A new `check-contrast-notes.ts` guard (G-11) asserts the documented ratios in DESIGN.md § 3 match the computed values.

**WCAG relative-luminance formula**:
```
L = 0.2126 * R + 0.7152 * G + 0.0722 * B
where R, G, B are linearized sRGB channels
contrast = (L1 + 0.05) / (L2 + 0.05)
```

**Decision**: JSON format (simpler than YAML, no parser dependency). The generator computes ratios from the token table — no hardcoded ratios.

## R7: DESIGN.md § 2 table split

The PO ruled (G8) that the § 2 catalog table is split into "Component Identity" + "Accessibility Obligations" sub-tables.

**Design**:
- **Component Identity**: selector, variants, required DOM structure, intended use.
- **Accessibility Obligations**: a11y obligations per component (roles, labels, focus, contrast, non-color cues).

This split makes the a11y contract independently auditable — a reviewer can check the a11y obligations without wading through the identity details.

**Decision**: Split the existing § 2 table into two sub-tables. Existing rows are reorganized; new rows follow the same structure.

## R8: HTML usage snippets in DESIGN.md § 2

The PO ruled (G10) that each § 2 catalog entry includes an HTML usage snippet.

**Design**:
- Each entry shows the canonical usage pattern (e.g., `<a class="europa-link" href="...">text</a>`).
- Snippets are illustrative, not exhaustive — they show the canonical pattern, not every variant.

**Decision**: Add a "Usage" column or a code block per entry. For compactness, a `Usage` column with inline code is preferred.

## R9: Preview page architecture

The spec (FR-042) requires a standalone design-system preview page.

**Options considered**:
1. **Static HTML in `packages/design/preview/`** — served via the existing Vite dev server. Self-contained, no console route.
2. **Console route** — adds a `/design` route to the console. More integrated but couples the design system to the console.

**Decision**: Option 1 (static HTML in the design package). The preview page is documentation, not a production route. Serving it via the design package's dev server keeps it self-contained and avoids adding a console route. The page imports `TOKENS` directly and builds swatches/tables from it — always reflecting current values.

## R10: Typography utility classes

The PO ruled (G5) that new typography utility classes are added (`.europa-heading-1/2/3`, `.europa-subheading`, `.europa-body`, `.europa-body-sm`, `.europa-caption`).

**Design**:
- These complement the existing `.europa-typography--*` semantic classes.
- They are layout-agnostic — carry only typography declarations (font-size, weight, color, line-height, letter-spacing).
- They compose only `--europa-*` tokens (no hex literals).

**Decision**: Add as a new FR-040a. The classes use the existing size/weight/color/line-height/tracking tokens — no new token values needed beyond the tracking tokens already added in FR-004.

## R11: Match row state modifiers

The PO ruled (G2) that match rows gain state modifiers (`.europa-lobby__row--waiting`, `--in-progress`, `--your-match`).

**Design**:
- `--waiting`: green left-border (`--europa-color-success`)
- `--in-progress`: amber left-border (`--europa-color-warning`)
- `--your-match`: accent background (`--europa-color-accent`) with `--europa-color-surface` text

The left-border treatment mirrors the identity-card accent (FR-027) for visual consistency.

**Decision**: Additive modifiers on the existing `.europa-lobby__row` base. The base style is unchanged.

## R12: Order bar mode active styling

The PO ruled (G3) that the order bar mode toggle's active state gains accent styling.

**Design**:
- `.europa-order-bar__mode--active`: `background-color: var(--europa-color-accent); color: var(--europa-color-page-bg)`
- Transition on background-color and color.

**Decision**: Additive modifier. The `aria-pressed` attribute and mode label text remain the primary identifiers (not color alone).

## R13: Feedback toast direction + position

The PO ruled (D1/D2) that the feedback toast slides from the LEFT and is anchored bottom-left.

**Design**:
- `@keyframes europa-toast-enter`: `translateX(-8px)` → `translateX(0)`, `opacity: 0` → `opacity: 1`
- `@keyframes europa-toast-exit`: `translateX(0)` → `translateX(-8px)`, `opacity: 1` → `opacity: 0`
- `.europa-feedback`: `position: fixed; bottom: var(--europa-spacing-lg); left: var(--europa-spacing-lg); z-index: 800`

**Decision**: Follow the PO ruling. The left position keeps toasts clear of the HUD (which sits right of the board on wide screens).

## R14: Error boundary + route notice icons

The PO ruled (G6/G7) that the error boundary and route notice gain icon styling.

**Design**:
- `.europa-error-boundary__icon`: `font-size: 4rem; line-height: 1`
- `.europa-error-boundary__details`: `font-family: var(--europa-typography-font-mono); font-size: var(--europa-typography-size-xs); color: var(--europa-color-text-muted)`
- `.europa-route-notice__icon`: `font-size: 3rem; line-height: 1; color: var(--europa-color-text-muted)`

**Decision**: Follow the PO ruling. Icons are decorative (supplementary to the message text) — no `aria-hidden` needed if the icon is an emoji/SVG with `aria-hidden="true"`.

## R15: Pre-composed duration token

The PO ruled (G1) that a `--europa-motion-duration: 120ms` pre-composed CSS token is added.

**Design**:
- `TOKENS.motion.duration = '120ms'` — the CSS `time` equivalent of the existing `durationMs` (120).
- Emitted as `--europa-motion-duration: 120ms`.

**Decision**: Additive token. The existing `durationMs` (number) remains for programmatic use; the new `duration` (string) is for CSS `transition` shorthand.

## Alternatives Considered and Rejected

| Alternative | Rejected Because |
|-------------|------------------|
| **JS tooltip** (positioning, `aria-describedby`) | Spec explicitly requires CSS-only; content is redundant with visible text |
| **Console route for preview page** | Couples the design system to the console; static HTML in the design package is self-contained |
| **YAML for contrast notes** | JSON is simpler, no parser dependency, and the design package already uses JSON for `tokens.json` |
| **`@supports` guard for `backdrop-filter`** | Unnecessary — the property degrades gracefully (browser ignores unknown property) |
| **New breakpoint tokens** | The spec's breakpoints are inline media queries; no token abstraction needed |
| **New web components for link/divider/tooltip/etc.** | Spec Out of Scope; CSS-only classes are sufficient and simpler |
